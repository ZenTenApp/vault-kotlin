# Vault Key setup

## User outcome

A new user sets up ZenTen Vault with the private key and passphrase for an existing Ed25519 OpenSSH Vault Key. This material establishes the vault identity used for backup and recovery. The in-app generation path also presents the Brave recovery mnemonic as 24 BIP-39 word-list indices, grouped into eight transcription-friendly rows of three.

## Current behavior

1. The user opens **Get started** and selects **Login with VaultKey**, which proceeds to **Setup VaultKey Account**. **Create VaultKey** opens the implemented generation and backup screens (an unrecoverable-loss warning and consent gate, **Create Passphrase**, **Re-enter Passphrase**, **Create Backup**, and **Confirm Backup**). The federated sign-in actions remain design placeholders that report "coming soon".
2. On **Setup VaultKey Account**, the user copies a passphrase-protected OpenSSH private key and selects **Paste VaultKey**. The app reads the first clipboard item without displaying it, clears the clipboard immediately, and validates that it is a supported encrypted OpenSSH-v1 Ed25519 container before proceeding to the passphrase step. PEM, raw Base64, and the supported `{"OPENSSH PRIVATE KEY":"..."}` wrapper are accepted; malformed, unencrypted, non-Ed25519, and unsupported containers are rejected on the paste step.
3. The app validates the material locally and derives the vault identity.
4. The app stores the Vault Key securely and attempts all enabled sources sequentially.
5. Setup completes only after at least one eligible Nostr relay and one eligible Brave Sync server already contain or acknowledge the Vault Key backup.
6. The app then schedules source consolidation, which discovers and restores associated accounts before repairing remote gaps.

If remote quorum is unavailable, setup remains incomplete but the validated Vault Key stays in secure local storage. The user can retry backup without pasting or deriving the Vault Key again.

For an in-app generated VaultKey, successful passphrase verification is the irreversible commit point. Vault immediately opens a non-dismissible **Creating VaultKey** screen with no Back action, the passphrase hero artwork, and a warning not to close the app. The screen reports whether Vault is creating the encrypted key, saving it in keystore-backed storage, or syncing the VaultKey account. During sync it shows the active backup-source label and the completed/total source count. Vault records the next wizard step and checks/writes the Vault Key on every enabled backup source before showing **Create Backup**. For this initial create-flow operation only, Nostr relay reads, encryption, event signing, publication, and NIP-42 authentication use the NIP-06 identity derived from the 24-word mnemonic of Seedify's `brave` associated account. Brave Sync uses those same 24 words plus its date-derived 25th word. The original encrypted VaultKey remains the backed-up payload, while the securely stored Vault Key retains its normal original-seed Nostr identity for later backup and consolidation. A later consolidation can therefore create a duplicate relay Vault Key backup under that normal identity. Individual source failures are retained for later repair and do not return the user to key generation. Closing or leaving the app resumes **Create Backup**, **Confirm Backup** after Android has accepted the local export, or **Save your Secret Combinations** after the pasted key matches. Back navigation is disabled from **Create Backup** toward key generation so another identity cannot be generated accidentally; **Confirm Backup** may return to **Create Backup** to export again. After saving the combinations, the user must verify all 24 indices sequentially on **Secret Combinations**. One navigation-graph-scoped flow ViewModel owns creation, backup, and recovery-code verification state. During key creation it derives the Brave recovery indices while the decrypted SSH seed is already in memory, so normal navigation performs no additional SSH KDF work. The save and verification screens share that in-memory result for the rest of the wizard session. Only after process restart, when the generated data is no longer in memory, does the screen show loading feedback while it decrypts the persisted VaultKey once on a background dispatcher and re-derives the indices. Successful verification opens a minimal completion screen with a large outlined check icon. After three seconds, Vault automatically marks setup complete and opens the account list. If the app closes during that interval, it resumes on the completion screen and repeats the short delay.

The **Creating VaultKey** status is presented as a terminal-style transcript. The current operation remains encoded as continuously changing white glyphs at 25% opacity until it actually completes, then resolves to bold white feedback text before the next line starts. The sequence covers encrypted VaultKey creation, Nostr key-pair derivation, Sync Code derivation, and every enabled backup source in configured order; relay and Sync Server lines are numbered independently. The transcript never derives glyphs from key material or claims an operation completed early. Accessibility services receive a neutral in-progress status rather than the encoded glyphs. When all source attempts finish, the screen shows **VaultKey created successfully** with a circular checkmark for two seconds before opening **Create Backup**. Android's disabled-animation setting keeps the pending line statically encoded instead of churning or revealing completion early.

## Failure and security expectations

- Invalid input and wrong-passphrase errors must not echo private-key or passphrase content. When creating a VaultKey in-app, Vault requires at least 8 passphrase characters with at least one uppercase letter, one lowercase letter, one number, and one non-whitespace special character; the flow cannot advance until every rule is met. The Create VaultKey wizard reports a passphrase mismatch and a key-generation failure with fixed messages that contain no key or passphrase material.
- In the Create VaultKey wizard, the chosen passphrase remains only in the graph-scoped ViewModel until verification. The generated account (including the encrypted SSH key and passphrase needed by current backup adapters) is then written to keystore-backed encrypted storage before remote backup starts. Only a non-secret wizard-step marker is stored in DataStore. Neither secret is placed in navigation arguments. After the exported key is verified, the app derives the Brave associated-account seed and shows the one-based English BIP-39 positions of its 24 mnemonic words; it does not persist a second copy of these displayed values.
- The private key is never rendered during import. It remains in memory only while the passphrase step is active and is discarded if the user returns to the paste step.
- Clipboard clearing is best-effort: Vault clears Android's current clipboard entry before proceeding, but the operating system, a keyboard, or another clipboard-history provider may retain an earlier copy outside Vault's control. If Vault cannot read or clear the clipboard, it does not proceed.
- The setup screen is protected from screenshots on supported Android devices.
- Every passphrase field requests password input semantics from the keyboard, including when the passphrase is temporarily visible. This disables IME autocorrection and suggestions so punctuation such as `.` is entered literally without an automatically inserted space.
- The primary setup action is unavailable while processing is in progress.
- The Vault Key is not shown as a normal associated-account item; its per-source state is available from the dedicated **Vault Key** screen.
- Quorum failure messages identify whether relay or Brave Sync coverage is missing without exposing source credentials or secret material.

## Current limitations

- The current UI supports clipboard paste only. Manual text entry, file import, and QR intake are not available.
- In-app vault-key generation (**Create VaultKey**) is implemented through **Secret Combinations**. **Verify** matches the passphrases and opens **Creating VaultKey**, which has no Back action and provides stage-level creation feedback plus source-by-source synchronization progress. Vault generates an encrypted Ed25519 OpenSSH VaultKey, stores it locally, and attempts backup on all enabled sources. **Export VaultKey** uses the same direct local-backup target picker and canonical key representation as associated-account creation: raw Base64 without OpenSSH PEM wrappers or line breaks. Vault then requires the user to paste the exported key, clears the clipboard, validates its encrypted Ed25519 OpenSSH format, and confirms it exactly matches the stored VaultKey. A successful match advances to **Save your Secret Combinations**, where the 24 one-based BIP-39 indices are grouped in eight rows of three. A compact warning directs the user to write down all eight combinations and store them offline, and explains that Vault cannot restore lost combinations. A three-row snapping picker keeps the centered row fully opaque and fades its neighbors; edge padding allows the first and last rows to become centered without looping. The values can be hidden and gate the inactive **Continue** action behind acknowledgement that all eight combinations were saved. **Continue** opens a verification screen that accepts only the current numeric segment: a correct value automatically focuses the next segment and advances to the next row after each complete combination, while an incorrect value receives an error border. The picker cannot be manually scrolled, uses numbered row labels matching the saved-combinations screen, and preserves entered verification values when the user navigates back to review the combinations and then returns. After all segments match, a resumable completion screen shows only a large centered outlined check icon. After three seconds it automatically marks setup complete, removes the wizard from navigation history, and opens **Accounts**.
- Federated sign-in (Google, Apple, Microsoft) is not implemented. Its meaning for a key-rooted vault is an open product decision, since the root of trust is a keypair rather than a provider account.
- Production review is still required for supported key formats, error language, storage, backup destinations, and end-to-end setup recovery.
