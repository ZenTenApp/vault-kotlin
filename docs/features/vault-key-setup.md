# Vault Key setup

## User outcome

A new user sets up ZenTen Vault with the private key and passphrase for an existing Ed25519 OpenSSH Vault Key. This material establishes the vault identity used for backup and recovery. The in-app generation path also presents the `vkbckp` (Vault Key BacKup) recovery mnemonic as 24 BIP-39 word-list indices, grouped into eight transcription-friendly rows of three.

## Current behavior

1. The user opens **Get started** and selects **Login with VaultKey**, which proceeds to **Setup VaultKey**. **Recover VaultKey** accepts the eight saved Secret Combinations in a three-row snapping wheel: all eight rows can be scrolled, every field remains editable, and the centered row is elevated while adjacent rows fade toward the edges. Keyboard **Next** moves between fields, four-digit values advance automatically, and a persistent **Continue** action validates the complete input. Missing or out-of-range fields are highlighted individually; an invalid BIP-39 checksum produces a combination-level error while retaining all values for correction. It validates their BIP-39 range and checksum, then asks for the VaultKey passphrase on a separate screen. The 24 words alone derive both recovery addresses: the Nostr identity under which Vault Key relay records were published and the Brave Sync code. It queries enabled Nostr relay and Brave Sync sources that are trusted for restore for the `vaultkey` record, and tries every copy they hold newest-first. A copy is accepted only when the passphrase decrypts a valid encrypted Ed25519 OpenSSH key **and** that key's seed re-derives to the exact 24 Secret Combinations the user entered; the decrypted key is then stored securely, setup is marked complete, Accounts opens, and consolidation is scheduled. A source that is unreachable, or a copy that is corrupt or belongs to another key, does not stop the remaining copies and sources; connectivity is reported separately from a genuinely absent record, and a misbound copy is reported distinctly from absence. **Create VaultKey** opens the implemented generation and backup screens (an unrecoverable-loss warning and consent gate, **Create Passphrase**, **Re-enter Passphrase**, **Create Backup**, and **Confirm Backup**). The federated sign-in actions remain design placeholders that report "coming soon".
2. On **Setup VaultKey**, the user copies a passphrase-protected OpenSSH private key and selects **Paste VaultKey**. The app reads the first clipboard item without displaying it, clears the clipboard immediately, and validates that it is a supported encrypted OpenSSH-v1 Ed25519 container before proceeding to the passphrase step. PEM, raw Base64, and the supported `{"OPENSSH PRIVATE KEY":"..."}` wrapper are accepted; malformed, unencrypted, non-Ed25519, and unsupported containers are rejected on the paste step. The container's declared `bcrypt_pbkdf` work factor must be between 128 and 8192 rounds; a key outside that band is rejected here, before the passphrase is requested, because its encrypted form would be too weak for a key that leaves the device — or, at the top end, expensive enough to stall unlock. A rejected **Recover VaultKey** copy is skipped and the remaining copies and sources are still tried.
3. The app validates the material locally and derives the vault identity.
4. The app stores the Vault Key securely and attempts all enabled sources sequentially.
5. Setup completes only after at least one eligible Nostr relay and one eligible Brave Sync server already contain or acknowledge the Vault Key backup.
6. The app then schedules source consolidation, which discovers and restores associated accounts before repairing remote gaps.

If remote quorum is unavailable, setup remains incomplete but the validated Vault Key stays in secure local storage. `SetupService.performSetup` records a durable `AppStorageService.importedVaultKeySetupPending` flag once the key is committed, so a post-persistence backup or prerequisite failure is distinguishable from a parse/derivation failure (which persists nothing). The setup screen immediately offers **Retry backup without re-importing**, and a retry re-attempts the enabled sources with the stored key. If the process dies before quorum, the launch router sees the pending flag after the normal device-authentication and VaultKey-passphrase gate and reopens **Setup VaultKey** in a retry-only state instead of **Get started**, so the committed identity cannot be replaced by starting a new import or generation flow. A successful retry marks setup complete and clears the pending flag; `AppStorageService.clearSetupComplete` also clears it when setup is restarted.

For an in-app generated VaultKey, successful passphrase verification is the irreversible commit point. Vault immediately opens a non-dismissible **Creating VaultKey** screen with no Back action, the passphrase hero artwork, and a warning not to close the app. The screen reports whether Vault is creating the encrypted key, saving it in keystore-backed storage, or syncing the VaultKey account. During sync it shows the active backup-source label and the completed/total source count. Vault records the next wizard step and checks/writes the Vault Key on every enabled backup source before showing **Create Backup**. Every Vault Key relay operation — this initial create-flow backup, imported-key setup, retries, and later consolidation — uses the NIP-06 identity derived from the 24-word mnemonic of Seedify's `vkbckp` (Vault Key BacKup) associated account for reads, NIP-44 encryption, event signing, publication, and NIP-42 authentication, because that identity is the only one recoverable from the written-down words. `DefaultBackupSourceFactory` derives it once per engine operation and passes it to `NostrBackupSource`, which has no stored identity to fall back to, so every run addresses the same relay record (`kind` 37801, `d` = `vaultkey`) and the index-before-write check never publishes a duplicate under a second identity. The original encrypted VaultKey remains the backed-up payload, while associated-account records use the Vault Key's original-seed identity, re-derived from the decrypted seed per run. Brave Sync uses those same 24 words plus its date-derived 25th word. Individual source failures are retained for later repair and do not return the user to key generation. Closing or leaving the app resumes **Create Backup**, **Confirm Backup** after Android has accepted the local export, or **Save your Secret Combinations** after the pasted key matches. Back navigation is disabled from **Create Backup** toward key generation so another identity cannot be generated accidentally; **Confirm Backup** may return to **Create Backup** to export again. A paste that is not a supported key or does not match the stored VaultKey counts as a failed attempt: the first three failures show a safe error and block the wizard for one, two, and then three minutes behind a non-dismissible countdown that also disables Back, and the fourth returns to **Create Backup** and resets the counter so a fresh export begins a new cycle. The counter and the non-secret block deadline survive process restart. A clipboard-read, clipboard-clear, or storage failure is not counted because it is not a wrong key. After saving the combinations, the user must verify all 24 indices sequentially on **Secret Combinations**. One navigation-graph-scoped flow ViewModel owns creation, backup, and recovery-code verification state. During key creation it derives the `vkbckp` Vault Key backup recovery indices while the decrypted SSH seed is already in memory, so normal navigation performs no additional SSH KDF work. The save and verification screens share that in-memory result for the rest of the wizard session. Only after process restart, when the generated data is no longer in memory, does the screen show loading feedback while it decrypts the persisted VaultKey once on a background dispatcher and re-derives the indices. Successful verification marks setup complete and opens the account list directly, but only when the remote backup quorum recorded by the create-flow backup is satisfied. When it is not, the verification screen stays open with an explanation that no relay plus Brave Sync copy of the VaultKey was confirmed and a **Retry VaultKey backup** action. The retry re-attempts every enabled source with the retained local Vault Key; reaching quorum there completes setup and opens the account list, while another failure keeps the same blocked state. Setup therefore never completes on an exported-and-transcribed key alone: the transcribed Secret Combinations prove the user kept a recovery copy, and the quorum check proves a remote recovery copy exists.

The **Creating VaultKey** status is presented as a terminal-style transcript. The current operation remains encoded as continuously changing white glyphs at 25% opacity, refreshing at 20 frames per second, until it actually completes, then resolves to bold white feedback text before the next line starts. The sequence covers encrypted VaultKey creation, VaultKey seed derivation, Sync Code derivation, and every enabled backup source in configured order; relay and Sync Server lines are numbered independently. The transcript never derives glyphs from key material or claims an operation completed early. Accessibility services receive a neutral in-progress status rather than the encoded glyphs. When all source attempts finish, the screen shows **VaultKey created successfully** with a circular checkmark for two seconds before opening **Create Backup**. Android's disabled-animation setting keeps the pending line statically encoded instead of churning or revealing completion early.

After setup, the same 24 positions can be re-displayed and re-verified from **Settings → Secret Combinations**. That passphrase-gated flow is separate from creation, cannot be cancelled once entered, and resumes after a restart; it is documented in [Secret Combinations review](secret-combinations-review.md).

## Failure and security expectations

- Invalid input and wrong-passphrase errors must not echo private-key or passphrase content. Recovery distinguishes invalid combination structure, missing remote records, and connectivity failures; authentication/decryption failures use a combined safe credentials error. The Create VaultKey wizard reports a passphrase mismatch and a key-generation failure with fixed messages that contain no key or passphrase material.
- When creating a VaultKey in-app, Vault requires at least 12 passphrase characters and a zxcvbn guessability bucket of at least 3 — zxcvbn's "safely unguessable against an offline attack that assumes a salted, slow hash function" band, which is the `bcrypt_pbkdf` class protecting the VaultKey. The flow cannot advance until both rules are met. The step presents them as two stacked rows — a **Minimum 12 characters** requirement and a five-segment strength meter — rather than a side-by-side checklist, because the two answer different questions. The meter fills red below the floor and green at or above it, animates that hand-off, and keeps empty segments visible as a neutral track. Its label row states the band in words — "Passphrase Strength: Strong" — and the concrete crack-time estimate, the offline slow-hash one that matters because a stolen backup can be attacked with no rate limit, lives in the sheet instead; the row is exposed to accessibility services as a single "Passphrase Strength: Strong" node rather than as five decorative shapes. An info button beside the bar opens a **Passphrase strength** sheet that explains the rating: the score directly under the bar, both offline crack-time scenarios side by side (the slow hash Vault actually uses, next to what a fast hash would cost), every match in the estimator's decomposition, named by the text that matched and the pattern that matched it with its pattern-specific detail, and all of its suggestions. The matched text is rendered deliberately, so this sheet shows fragments of the passphrase and is the only place besides the input field that does. Character-class composition rules (an uppercase letter, a lowercase letter, a number, a symbol) were deliberately dropped: they push users toward exactly the predictable mutations — `Password1!`, `P@ssw0rd` — that a strength estimator already rejects, while rejecting long passphrases that happen to contain no digit. The estimator is told that this product's own names (`zenten`, `vault`, `vaultkey`) are common, so a weak tail such as `vaultkey1234!` cannot ride on them. Passphrases longer than 256 characters are refused rather than estimated, which bounds the pattern search instead of approximating a score from a prefix.
- Passphrase strength is measured entirely on-device with no network call and no breach-list lookup. Only the non-secret projection reaches the ViewModel and the UI; the candidate passphrase is held in a wipeable buffer that is cleared as soon as matching finishes. Measurement is debounced behind a typing pause and runs off the main thread, and the cached measurement is dropped when the step is left.
- The **Passphrase strength** sheet explains a rating from the estimator's projection, which carries passphrase fragments on purpose: each finding is named by the text that matched, alongside its pattern, span, and cost, because a pattern and a span alone cannot tell `alice@` from any other six-character run. That makes the sheet the one place besides the input field that renders passphrase content. It is a modal the user opens deliberately, it sits under the app's screenshot protection, and the projection lives only in the graph-scoped ViewModel and is dropped when the step is left. `Strength.password` and the de-obfuscated `Match.matchedWord` are still not carried.
- In the Create VaultKey wizard, the chosen passphrase remains only in the graph-scoped ViewModel until verification. The generated account (the passphrase-encrypted SSH key, and nothing derived from it) is then written to keystore-backed encrypted storage before remote backup starts; the Nostr identities used for backup are derived from that key's seed per engine run and are never stored; the passphrase itself is moved to the in-memory `VaultKeySession` and is never written to disk. Only a non-secret wizard-step marker is stored in DataStore. Neither secret is placed in navigation arguments. After the exported key is verified, the app derives the `vkbckp` (Vault Key BacKup) associated-account seed and shows the one-based English BIP-39 positions of its 24 mnemonic words; it does not persist a second copy of these displayed values.
- The private key is never rendered during import. It remains in memory only while the passphrase step is active and is discarded if the user returns to the paste step.
- **Confirm Backup** rate-limits wrong pastes so the exported key cannot be brute-forced from the device. Each failed paste shows a safe error and blocks the wizard for an additional minute (first failure one minute, then two, then three) behind a non-dismissible countdown that also disables Back; the fourth failure returns to **Create Backup** and clears the counter. Only failed validation and mismatches count, and the persisted counter records only the attempt count and the non-secret deadline — never the pasted key or the stored key.
- Clipboard clearing is best-effort: Vault clears Android's current clipboard entry before proceeding, but the operating system, a keyboard, or another clipboard-history provider may retain an earlier copy outside Vault's control. If Vault cannot read or clear the clipboard, it does not proceed.
- The setup screen is protected from screenshots on supported Android devices.
- Every passphrase field requests password input semantics from the keyboard, including when the passphrase is temporarily visible. This disables IME autocorrection and suggestions so punctuation such as `.` is entered literally without an automatically inserted space.
- The primary setup action is unavailable while processing is in progress.
- The Vault Key is not shown as a normal associated-account item; its per-source state is available from the dedicated **Vault Key** screen. That screen offers an **Export VaultKey to Notes** action at the top that first asks the user to re-enter the passphrase protecting the VaultKey, then sends the same self-describing encrypted VaultKey text through the in-app target picker as the creation-time export, without the paste-back confirmation used during creation.
- Quorum failure messages identify whether relay or Brave Sync coverage is missing without exposing source credentials or secret material.
- Before any remote backup, setup, retry, and the create-flow backup consult `RemoteOperationPrecondition`. Unless Android reports validated internet and the device clock is not known to be wrong, Vault persists or keeps the Vault Key locally and reports a retryable failure instead of signing timestamped Nostr backup events or Brave Sync authentication tokens. A time-source outage alone does not block setup because it is not proof of incorrect device time.

## Current limitations

- Passphrase strength is enforced only on the in-app **Create VaultKey** path. **Recover VaultKey** and **Paste VaultKey** accept a passphrase the user did not choose and show no warning about it: it cannot be gated, because refusing it would leave a user holding a valid key unable to onboard or recover, and re-encrypting the container is an out-of-band operation the app does not offer. This is a recorded decision (D9), not an unaddressed gap; see [Security model](../technical/security-model.md#required-production-review-topics).
- The bundled strength estimator's dictionaries are a compact English- and US-centric subset (common passwords, English Wikipedia words, US census names and surnames, US TV and film). Passphrases built from other languages or from uncommon domain vocabulary may be scored more generously than they deserve.
- A passphrase longer than 256 characters fails the strength rule rather than being measured, and the UI does not state that limit; the checklist simply keeps the rule unmet.
- The passphrase rules cover length and guessability only. There is no check against a live breach corpus such as Have I Been Pwned, which would require a network call this flow deliberately avoids.
- The improvement suggestions shown in the **Passphrase strength** sheet come from the estimator and are English-only library text. The crack-time wording and the finding names are app-owned `strings.xml` entries; the estimator's are not.
- The current UI supports clipboard paste only. Manual text entry, file import, and QR intake are not available.
- In-app vault-key generation (**Create VaultKey**) is implemented through **Secret Combinations**. **Verify** matches the passphrases and opens **Creating VaultKey**, which has no Back action and provides stage-level creation feedback plus source-by-source synchronization progress. Vault generates an encrypted Ed25519 OpenSSH VaultKey, stores it locally, and attempts backup on all enabled sources. **Export VaultKey** uses the same direct local-backup target picker and self-describing export format as associated-account creation: OpenSSH PEM markers around a one-line Base64 body, followed on separate lines by the account `npub`, raw creation ID/timestamp, the fixed display name `VaultKey`, and the account-card-style `Created on ...` date. Vault then requires the user to paste the exported text, clears the clipboard, validates its encrypted Ed25519 OpenSSH format, and confirms it exactly matches the stored VaultKey. A successful match advances to **Save your Secret Combinations**, where the 24 one-based BIP-39 indices are grouped in eight rows of three. A compact warning directs the user to write down all eight combinations and store them offline, and explains that Vault cannot restore lost combinations. A three-row snapping picker keeps the centered row fully opaque and fades its neighbors; edge padding allows the first and last rows to become centered without looping. The values can be hidden and gate the inactive **Continue** action behind acknowledgement that all eight combinations were saved. **Continue** opens a verification screen that accepts only the current numeric segment: a correct value automatically focuses the next segment and advances to the next row after each complete combination, while an incorrect value turns to the error color and semi-bold weight (no border) and an "Incorrect Secret Combination! Please try again." message appears below the picker. The picker cannot be manually scrolled, uses numbered row labels matching the saved-combinations screen, and preserves entered verification values when the user navigates back to review the combinations and then returns. After all segments match, Vault completes setup only if the create-flow backup reached the relay-plus-Brave quorum; otherwise the screen states that the remote backup is unconfirmed and offers **Retry VaultKey backup** in place of the picker. On a reached quorum it marks setup complete, removes the wizard from navigation history, and opens **Accounts** directly.
- Federated sign-in (Google, Apple, Microsoft) is not implemented. Its meaning for a key-rooted vault is an open product decision, since the root of trust is a keypair rather than a provider account.
- Production review is still required for supported key formats, error language, storage, backup destinations, and end-to-end setup recovery.
