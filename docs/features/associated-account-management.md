# Associated account management

## User outcome

After setup has satisfied the Vault Key backup quorum, a user can generate a separate Ed25519 SSH account for another service, project, or environment and find it in **My Accounts**.

## Current behavior

1. From **Accounts**, the user selects the bottom-centered **Create New Account** button.
2. The app displays **Create New Account** with the shared header row (an icon-only back arrow beside the centered title) and a **VaultKey Passphrase** field. The user can show or hide the entered passphrase and selects **Verify Passphrase**.
3. After the app verifies the passphrase against the securely retained vault-key passphrase, it asks for a mandatory **Account Name** containing 8 to 128 characters after surrounding whitespace is removed.
4. The user enters the account name and selects **Create Account**, or uses the Back link to return without creating one. There is no separate Cancel button. During key derivation, the primary button displays a spinner and **Creating Account** while the cryptographic work runs off the UI thread.
5. The app re-verifies the passphrase, rejects the request when 99 associated accounts already exist, then verifies that Vault Key setup is complete, meaning its required backup quorum was satisfied.
6. The app allocates a unique creation ID, generates the key pair encrypted with the verified Vault Key passphrase, derives its Nostr key pair from that SSH key, and saves both identities and the account name locally.
7. Targeted consolidation starts after the local save. It reconciles only the new account, indexes every source, and writes only where its canonical ID is absent; it never blindly pushes another entry to a source that already has the account.
8. Before the account can be used, the app opens **Export Account**, which requires the user to send a self-describing text backup to a chosen app through the in-app target picker via **Export to Notes**. The target picker dialog is titled **Export Account**. The payload contains the passphrase-encrypted OpenSSH private key as PEM with its Base64 body on one line, followed on separate lines by the account `npub`, the raw creation ID/timestamp, display name, and the full human-readable `Created on ...` date and time shown on the account-detail card. Once Android accepts the target, the flow advances to **Confirm Backup**.
9. **Confirm Backup** requires the user to copy the saved text back from the receiving app and paste it in with **Paste Account Key**. It reads the clipboard item without displaying it, clears the clipboard immediately, accepts the same PEM, raw Base64, and `{"OPENSSH PRIVATE KEY":"..."}` wrapper forms used elsewhere, and confirms the normalized encrypted Ed25519 OpenSSH container exactly matches the account's stored key. A mismatched, malformed, or unreadable paste reports a safe error and keeps this step open; a match marks the export complete.
10. After the pasted key matches, the app clears the pending export and queues durable background publication of a kind `0` Nostr profile and a kind `10050` DM relay list. The profile sets `name` to the account creation ID and `display_name` to the mandatory account name; `banner`, `picture`, and `about` are published as blank. The kind `10050` event has empty content and `relay` tags for `wss://dm1.zentext.me`, `wss://dm2.nostr.box`, and `wss://dm3.npub.cx`, advertising where NIP-17 clients should deliver messages to that account. Both events are signed with the associated account's Nostr key and published with backoff until all configured profile relays (`wss://user.kindpag.es`, `wss://purplepag.es`, `wss://directory.yabu.me`, `wss://profiles.nostr1.com`, `wss://relay.primal.net`, `wss://relay.snort.social`, `wss://nos.lol`) acknowledge them. The same relay set is queried when fetching kind `0` profiles.
11. The account appears in **Accounts**. Selecting it opens its identity and backup-status details.

The landing screen has a centered **Accounts** title and no Back action because it is the app's main destination. A settings cog at the top right opens **Settings**, where the **Vault Key** item opens Vault Key backup details. A labeled **Create New Account** button stays centered at the bottom over a subtle gradient and shadow so the primary action remains prominent without obscuring the account list.

Associated accounts use neutral cards and are listed newest first by their creation ID. Accounts are grouped by creation month, marked by a centered month label between horizontal separators. Each list card and its account-detail identity card show the latest nonblank kind `0` `display_name`, falling back first to the locally persisted account name and then to the shortened NIP-19 identity (`npub...` plus the final four characters). Display and account names use the available row width and are ellipsized only when they exceed it. Both cards show the nearly full-width 16-digit creation ID in groups of four. The list card shows a date-only local creation date such as `Created on Sep 2, 2026`, while the account-detail identity card keeps the full local date and time such as `Created on Wed Sep 2, 2026 11:56 AM`. Below the identity card, the detail screen shows the account's full locally derived NIP-19 `npub` in a dedicated card. The value includes an inline copy icon at the end of the text, and tapping anywhere on that text element copies it. A separate card below the Nostr identity shows the copyable SSH public-key line, whose trailing comment is the account's `npub`. Below that, the SHA-256 SSH public-key fingerprint uses the same inline icon and tap-to-copy behavior, followed by the bcrypt KDF round count read from the encrypted OpenSSH container without decrypting it. Below the fingerprint card, **Export Account to Notes** asks the user to re-enter the passphrase that protects the account, then opens the same in-app target picker used during creation and sends the identical self-describing export text; a second button, **Export Account to Clipboard**, uses the same passphrase gate and copies just the encrypted key as an OpenSSH PEM block (no account metadata) to the clipboard instead. Neither requires the paste-back confirmation used by the mandatory creation flow. Selecting anywhere on a list card opens the account backup-status details. The Vault Key remains an internal recovery identity and does not appear in the routine account list.

## Failure and security expectations

- Creation is rejected before local persistence when Vault Key backup quorum has not been satisfied; no associated account or backup job is created.
- A user can create at most 99 associated accounts. The 100th creation attempt is rejected with a clear message before any key material is generated or persisted. This ceiling applies only to user-initiated creation; accounts restored by consolidation or recovery are not counted against or blocked by it.
- Once Vault Key quorum is satisfied, a newly created associated account remains locally available even when remote consolidation must run again later.
- Creation requires the user to re-enter the vault-key passphrase. The app compares it with the securely retained Vault Key passphrase before persistence, and encrypts the generated OpenSSH private key with that same passphrase.
- The voluntary **Export Account to Notes** and **Export Account to Clipboard** actions on account details require the user to re-enter the passphrase stored for that account before the export runs. A wrong or blank passphrase shows an inline error, keeps the export from running, and does not retain the entered value. Export verifies against the account's own passphrase because a restored account can keep the passphrase it was originally imported with. The mandatory creation-time export does not re-ask, because the account was just created with that passphrase.
- Creation requires an account name whose trimmed length is between 3 and 128 characters. The same validated value is persisted and published publicly as the Nostr `display_name`.
- Creation errors are shown without disclosing secret key material.
- Every persisted associated account includes its derived Nostr key pair. The account signs its own kind `0` profile, and its private key is not sent to relays.
- Profile presentation data is public and cached separately from encrypted account secrets. Cards retain the locally derived shortened `npub` as a reliable fallback when relay retrieval fails or `display_name` is missing.
- Tapping the public `npub`, the SSH public-key line, the SSH fingerprint, or their copy icons places only that displayed public identifier on the system clipboard; no private-key material is copied.
- Account details expose the copyable SSH public-key line (with the account's `npub` as its comment), the copyable SSH public-key fingerprint, and the encrypted container's non-secret bcrypt KDF round count for verification. Account details also offer voluntary **Export Account to Notes** and **Export Account to Clipboard** actions that release the same passphrase-encrypted private key used during creation: the notes export sends the full self-describing text (PEM block plus account metadata) through the in-app target picker, while the clipboard export copies only the OpenSSH PEM block. The mandatory encrypted private-key export still happens during account creation and additionally requires the user to paste the saved key back.
- The account list refreshes when the app returns to the foreground, including after recovery work.
- Profile retrieval is shared by the list and detail screens. Each relay connection receives bounded filters containing all requested account public keys, cached values render first, and each relay response updates cards independently. Overlapping list/detail requests reuse the active fetch, while later account-list refreshes retry previous relay failures.
- The mandatory local-backup flow is split into **Export Account** and **Confirm Backup**. Back navigation is blocked on **Export Account**; Back from **Confirm Backup** returns to **Export Account** so the key can be sent again. The flow completes only after the export target accepted the text and the user pasted the saved key back and it matched the stored account. The paste check proves only that the user retained a readable copy: Android cannot confirm that the receiving app kept the text or that it remains available.
- The exported text contains the passphrase-encrypted OpenSSH private key and public account metadata in this exact line order: PEM begin marker, one-line Base64 key, PEM end marker, `npub`, raw creation ID/timestamp, display name, and account-detail-style full `Created on ...` date and time. It remains sensitive: share recipients or anyone who learns the retained passphrase may be able to use the account.

## Current limitations

- Associated accounts cannot be renamed, rotated, deleted, or manually restored one at a time.
- The app has no vault-reset action.
- The creation screen offers a Back link before creation starts; it does not remove an already-created account.
- The app persists a pending account ID before entering the backup sequence, then resumes the required export step after an app restart. Resuming always restarts at the export/choose-app phase; the paste-back confirmation must be completed again after a restart. It records only account IDs and cannot verify the durability, privacy, or future availability of a shared copy.
