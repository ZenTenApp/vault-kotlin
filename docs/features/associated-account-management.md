# Associated account management

## User outcome

After setup has satisfied the Vault Key backup quorum, a user can generate a separate Ed25519 SSH account for another service, project, or environment and find it in **Accounts**.

## Current behavior

1. From **Accounts**, the user selects the bottom-centered **Create New Account** button.
2. The app displays **Create New Account** with the shared header row (an icon-only back arrow beside the centered title) and a **VaultKey Passphrase** field. The user can show or hide the entered passphrase and selects **Verify Passphrase**.
3. After the app verifies the passphrase by decrypting the stored VaultKey, it asks for a mandatory **Account Name** containing 3 to 128 characters after surrounding whitespace is removed. That name is stored on the account's backup records: a plain `label` tag on its kind `37802` relay event and a `label: <name>` note on its Brave Sync record. The name is readable by anyone who can list those records; the creation screen deliberately keeps this to the length hint rather than adding a publication warning (D4).
4. The user enters the account name and selects **Create Account**, or uses the Back link to return without creating one. There is no separate Cancel button. During key derivation, the primary button displays a spinner and **Creating Account** while the cryptographic work runs off the UI thread.
5. The app re-verifies the passphrase, rejects the request when 99 associated accounts already exist, then verifies that Vault Key setup is complete, meaning its required backup quorum was satisfied.
6. The app allocates a unique creation ID, generates the key pair encrypted with the verified Vault Key passphrase, and saves that encrypted key with the account name locally. No Nostr identity is stored; it is derived from the key only when a backup record needs to be signed.
7. Targeted consolidation starts after the local save. It reconciles only the new account, indexes every source, and writes only where its canonical ID is absent; it never blindly pushes another entry to a source that already has the account.
8. Before the account can be used, the app opens **Export Account**, which requires the user to send a self-describing text backup to a chosen app through the in-app target picker via **Export to Notes**. The target picker dialog is titled **Export Account**. The payload contains the passphrase-encrypted OpenSSH private key as PEM with its Base64 body on one line, followed on separate lines by the raw creation ID/timestamp, the account name (an empty line when the account has no name), and the full human-readable `Created on ...` date and time shown on the account-detail card. The account's `npub` is deliberately not exported. Once Android accepts the target, the flow advances to **Confirm Backup**.
9. **Confirm Backup** requires the user to copy the saved text back from the receiving app and paste it in with **Paste Account Key**. It reads the clipboard item without displaying it, clears the clipboard immediately, accepts the same PEM, raw Base64, and `{"OPENSSH PRIVATE KEY":"..."}` wrapper forms used elsewhere, and confirms the normalized encrypted Ed25519 OpenSSH container exactly matches the account's stored key. A mismatched, malformed, or unreadable paste reports a safe error and keeps this step open; a match marks the export complete.
10. After the pasted key matches, the app clears the pending export and marks the mandatory local backup complete. Nothing is published to public Nostr profile relays: the account's public metadata is limited to what its encrypted backup already carries (the `label` tag described in step 3), and no kind `0` profile or kind `10050` DM relay list is written.
11. The account appears in **Accounts**. Selecting it opens its identity and backup-status details.

The landing screen has a centered **Accounts** title and no Back action because it is the app's main destination. A settings cog at the top right opens **Settings**, where the **Vault Key** item opens Vault Key backup details. A labeled **Create New Account** button stays centered at the bottom over a subtle gradient and shadow so the primary action remains prominent without obscuring the account list.

Associated accounts use neutral cards and are listed newest first by their creation ID. Accounts are grouped by creation month, marked by a centered month label between horizontal separators. Each list card and its account-detail identity card show the account name stored with the account, which for a restored account is the name carried by its backup record's `label` tag or Brave Sync note. A restored record that carries no label shows neither the avatar icon nor the name text: the shortened NIP-19 `npub` is never used as a fallback, so an associated account is not presented as a Nostr identity. That card reserves the name row's height as blank space so its creation ID and date line up with named cards. No relay profile lookup is made for display names. Display and account names use the available row width and are ellipsized only when they exceed it. Both cards show the nearly full-width 16-digit creation ID in groups of four. The list card shows a date-only local creation date such as `Created on Sep 2, 2026`, while the account-detail identity card keeps the full local date and time such as `Created on Wed Sep 2, 2026 11:56 AM`. The detail screen shows no Nostr identity card: the account's `npub` is not displayed or copied anywhere in the app. It shows a copyable SSH public-key line with no trailing comment, deliberately avoiding a link to the account's Nostr key. Below that, the SHA-256 SSH public-key fingerprint uses the same inline icon and tap-to-copy behavior, followed by the bcrypt KDF round count read from the encrypted OpenSSH container without decrypting it. Below the fingerprint card, **Export Account to Notes** asks the user to re-enter the passphrase that protects the account, then opens the same in-app target picker used during creation and sends the identical self-describing export text; a second button, **Export Account to Clipboard**, uses the same passphrase gate and copies just the encrypted key as an OpenSSH PEM block (no account metadata) to the clipboard instead. Neither requires the paste-back confirmation used by the mandatory creation flow. Selecting anywhere on a list card opens the account backup-status details. The Vault Key remains an internal recovery identity and does not appear in the routine account list.

## Failure and security expectations

- Creation is rejected before local persistence when Vault Key backup quorum has not been satisfied; no associated account or backup job is created.
- A user can create at most 99 associated accounts. The 100th creation attempt is rejected with a clear message before any key material is generated or persisted. This ceiling applies only to user-initiated creation; accounts restored by consolidation or recovery are not counted against or blocked by it.
- Once Vault Key quorum is satisfied, a newly created associated account remains locally available even when remote consolidation must run again later.
- Creation requires the user to re-enter the vault-key passphrase. The app verifies it by decrypting the stored VaultKey before persistence, then encrypts the generated OpenSSH private key with that same passphrase. The passphrase itself is never persisted.
- The voluntary **Export Account to Notes** and **Export Account to Clipboard** actions on account details require the user to re-enter the passphrase protecting that account before the export runs; it is verified by decrypting the account's OpenSSH key, not against a stored copy. A wrong or blank passphrase shows an inline error, keeps the export from running, and does not retain the entered value. Export verifies against the account's own passphrase because a restored account can keep the passphrase it was originally imported with. The mandatory creation-time export does not re-ask, because the account was just created with that passphrase.
- Creation requires an account name whose trimmed length is between 3 and 128 characters. The same validated value is stored on the account and written to both of its backup records, where it is readable without the Vault Key passphrase.
- Creation errors are shown without disclosing secret key material.
- Each associated account is persisted as one self-describing encrypted record keyed by its creation ID, with no separate index to keep in sync. A save or removal is a single atomic preference edit, so an account created while consolidation is restoring other accounts cannot be lost from the list. Listing is derived by scanning the stored records and returns them in ascending creation-ID order; the Accounts list then sorts newest first for display. A record that cannot be decrypted, or whose stored creation ID disagrees with the key it is filed under, is skipped and left on disk rather than shown or deleted.
- A persisted associated account holds only its passphrase-encrypted OpenSSH key and name. Its Nostr identity is derived from that key when needed and is never stored: the account's private key is never sent to relays, and the Vault Key's own identity signs its backup records.
- The account name is not secret once the account is backed up: the kind `37802` `label` tag and the Brave Sync note are stored in plaintext on the remote source. A restored record that carries no label renders an empty name; the shortened `npub` is never substituted.
- The associated account's Nostr key pair remains internal to backup and consolidation. Its `npub` is not displayed, copied, or written into an export, and the SSH public-key line carries no comment, so nothing in the account UI or its backup text links the account to a Nostr identity.
- Tapping the SSH public-key line, the SSH fingerprint, or their copy icons places only that displayed public identifier on the system clipboard; no private-key material is copied.
- Account details expose the copyable SSH public-key line (without a comment), the copyable SSH public-key fingerprint, and the encrypted container's non-secret bcrypt KDF round count for verification. Account details also offer voluntary **Export Account to Notes** and **Export Account to Clipboard** actions that release the same passphrase-encrypted private key used during creation: the notes export sends the full self-describing text (PEM block plus account metadata) through the in-app target picker, while the clipboard export copies only the OpenSSH PEM block. The mandatory encrypted private-key export still happens during account creation and additionally requires the user to paste the saved key back.
- The account list refreshes when the app returns to the foreground, including after recovery work. Lists and details render from local storage only, so account names do not depend on relay or Brave Sync availability.
- The mandatory local-backup flow is split into **Export Account** and **Confirm Backup**. Back navigation is blocked on **Export Account**; Back from **Confirm Backup** returns to **Export Account** so the key can be sent again. The flow completes only after the export target accepted the text and the user pasted the saved key back and it matched the stored account. The paste check proves only that the user retained a readable copy: Android cannot confirm that the receiving app kept the text or that it remains available.
- The associated-account export contains the passphrase-encrypted OpenSSH private key and public account metadata in this exact line order: PEM begin marker, one-line Base64 key, PEM end marker, raw creation ID/timestamp, account name (empty when unnamed), and account-detail-style full `Created on ...` date and time. It deliberately omits the account `npub`, unlike the Vault Key export. It remains sensitive: share recipients or anyone who learns the passphrase may be able to use the account.

## Current limitations

- Associated accounts cannot be renamed, rotated, deleted, or manually restored one at a time.
- The app has no vault-reset action.
- The creation screen offers a Back link before creation starts; it does not remove an already-created account.
- The app persists a pending account ID before entering the backup sequence, then resumes the required export step after an app restart. Resuming always restarts at the export/choose-app phase; the paste-back confirmation must be completed again after a restart. It records only account IDs and cannot verify the durability, privacy, or future availability of a shared copy.
