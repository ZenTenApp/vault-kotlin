# Associated key management

## User outcome

After setup has satisfied the Vault Key backup quorum, a user can generate a separate Ed25519 SSH key for another service, project, or environment and find it in **Keys**.

## Current behavior

1. From **Keys**, the user selects the bottom-centered **Create New Key** button.
2. The app displays **Create New Key** with the shared header row (an icon-only back arrow beside the centered title) and a **VaultKey Passphrase** field. The user can show or hide the entered passphrase and selects **Verify Passphrase**.
3. After the app verifies the passphrase by decrypting the stored VaultKey, it asks for a mandatory **Key Name** containing 3 to 128 characters after surrounding whitespace is removed, and the name must not contain "vault key" in any spelling (see the naming rule below). That name is stored on the key's backup records: a plain `label` tag on its kind `37802` relay event and a `label:<name>` note on its Brave Sync record. The name is readable by anyone who can list those records; the creation screen deliberately keeps this to the length hint rather than adding a publication warning (D4).
4. The user enters the key name and selects **Create Key**, or uses the Back link to return without creating one. There is no separate Cancel button. During key derivation, the primary button displays a spinner and **Creating Key** while the cryptographic work runs off the UI thread.
5. The app re-verifies the passphrase, rejects the request when 99 associated keys already exist, then verifies that Vault Key setup is complete, meaning its required backup quorum was satisfied.
6. The app allocates a unique creation ID, generates the key pair encrypted with the verified Vault Key passphrase, and saves that encrypted key with the key name locally. No Nostr identity is stored; it is derived from the key only when a backup record needs to be signed.
7. Targeted consolidation starts after the local save. It reconciles only the new key, indexes every source, and writes only where its canonical ID is absent; it never blindly pushes another entry to a source that already has the key.
8. Before the key can be used, the app opens **Export Key**, which requires the user to send a self-describing text backup to a chosen app through the in-app target picker via **Export to Notes**. The target picker dialog is titled **Export Key**. The payload contains the passphrase-encrypted OpenSSH private key as PEM with its Base64 body on one line, followed on separate lines by `unixTimestamp:<creation ID>`, `label:<key name>` (empty after the colon when the key has no name), and `createdAt:<the full human-readable date and time shown on the key-detail card>`. The key's `npub` is deliberately not exported. Once Android accepts the target, the flow advances to **Confirm Backup**.
9. **Confirm Backup** requires the user to copy the saved text back from the receiving app and paste it in with **Paste Key**. It reads the clipboard item without displaying it, clears the clipboard immediately, accepts the same PEM, raw Base64, and `{"OPENSSH PRIVATE KEY":"..."}` wrapper forms used elsewhere, and confirms the normalized encrypted Ed25519 OpenSSH container exactly matches the key's stored key. A mismatched, malformed, or unreadable paste reports a safe error and keeps this step open; a match marks the export complete.
10. After the pasted key matches, the app clears the pending export and marks the mandatory local backup complete. Nothing is published to public Nostr profile relays: the key's public metadata is limited to what its encrypted backup already carries (the `label` tag described in step 3), and no kind `0` profile or kind `10050` DM relay list is written.
11. The key appears in **Keys**. Selecting it opens its identity and backup-status details.

The landing screen has a centered **Keys** title and no Back action because it is the app's main destination. A settings cog at the top right opens **Settings**, where the **Vault Key** item opens Vault Key backup details. A labeled **Create New Key** button stays centered at the bottom over a subtle gradient and shadow so the primary action remains prominent without obscuring the key list.

Associated keys use neutral cards and are listed newest first by their creation ID. Keys are grouped by creation month, marked by a centered month label between horizontal separators. Each list card and its key-detail identity card show the key name stored with the key, which for a restored key is the name carried by its backup record's `label` tag or Brave Sync note. A restored record that carries no label shows neither the avatar icon nor the name text: the shortened NIP-19 `npub` is never used as a fallback, so an associated key is not presented as a Nostr identity. That card reserves the name row's height as blank space so its creation ID and date line up with named cards. No relay profile lookup is made for display names. Display and key names use the available row width and are ellipsized only when they exceed it. Both cards show the nearly full-width 16-digit creation ID in groups of four. The list card shows a date-only local creation date such as `Created on Sep 2, 2026`, while the key-detail identity card keeps the full local date and time such as `Created on Wed Sep 2, 2026 11:56 AM`. The detail screen shows no Nostr identity card: the key's `npub` is not displayed or copied anywhere in the app. It shows a copyable SSH public-key line with no trailing comment, deliberately avoiding a link to the key's Nostr key. Below that, the SHA-256 SSH public-key fingerprint uses the same inline icon and tap-to-copy behavior, followed by the bcrypt KDF round count read from the encrypted OpenSSH container without decrypting it. Below the fingerprint card, **Export Key to Notes** asks the user to re-enter the passphrase that protects the key, then opens the same in-app target picker used during creation and sends the identical self-describing export text; a second button, **Export Key to Clipboard**, uses the same passphrase gate and copies just the encrypted key as an OpenSSH PEM block (no key metadata) to the clipboard instead. Neither requires the paste-back confirmation used by the mandatory creation flow. Selecting anywhere on a list card opens the key backup-status details. The Vault Key remains an internal recovery identity and does not appear in the routine key list.

## Failure and security expectations

- Creation is rejected before local persistence when Vault Key backup quorum has not been satisfied; no associated key or backup job is created.
- A user can create at most 99 associated keys. The 100th creation attempt is rejected with a clear message before any key material is generated or persisted. This ceiling applies only to user-initiated creation; keys restored by consolidation or recovery are not counted against or blocked by it.
- Once Vault Key quorum is satisfied, a newly created associated key remains locally available even when remote consolidation must run again later.
- Creation requires the user to re-enter the vault-key passphrase. The app verifies it by decrypting the stored VaultKey before persistence, then encrypts the generated OpenSSH private key with that same passphrase. The passphrase itself is never persisted.
- The voluntary **Export Key to Notes** and **Export Key to Clipboard** actions on key details require the user to re-enter the passphrase protecting that key before the export runs; it is verified by decrypting the key's OpenSSH key, not against a stored copy. A wrong or blank passphrase shows an inline error, keeps the export from running, and does not retain the entered value. Export verifies against the key's own passphrase because a restored key can keep the passphrase it was originally imported with. The mandatory creation-time export does not re-ask, because the key was just created with that passphrase.
- Creation requires a key name whose trimmed length is between 3 and 128 characters. The name must not contain the term "vault key" in any form: matching ignores case, spaces, punctuation, and symbols, and folds full-width or compatibility letters to their plain form, so "Vault Key", "VAULT-KEY", "v a u l t k e y", and "ｖａｕｌｔｋｅｙ" are all rejected. The screen shows `Key name cannot contain "vault key"` in place of the length hint and keeps **Create Key** disabled; `KeyService.createAssociatedKey` enforces the same rule and returns that message if the name gets past the screen. Look-alike letters from other scripts (for example Cyrillic) are not folded, so they are not matched. Existing names are not re-checked; the rule applies to creation only. The same validated value is stored on the key and written to both of its backup records, where it is readable without the Vault Key passphrase.
- Creation errors are shown without disclosing secret key material.
- Each associated key is persisted as one self-describing encrypted record keyed by its creation ID, with no separate index to keep in sync. A save or removal is a single atomic preference edit, so a key created while consolidation is restoring other keys cannot be lost from the list. Listing is derived by scanning the stored records and returns them in ascending creation-ID order; the Keys list then sorts newest first for display. A record that cannot be decrypted, or whose stored creation ID disagrees with the key it is filed under, is skipped and left on disk rather than shown or deleted.
- A persisted associated key holds only its passphrase-encrypted OpenSSH key and name. Its Nostr identity is derived from that key when needed and is never stored: the key's private key is never sent to relays, and the Vault Key's own identity signs its backup records.
- The key name is not secret once the key is backed up: the kind `37802` `label` tag and the Brave Sync note are stored in plaintext on the remote source. A restored record that carries no label renders an empty name; the shortened `npub` is never substituted.
- The associated key's Nostr key pair remains internal to backup and consolidation. Its `npub` is not displayed, copied, or written into an export, and the SSH public-key line carries no comment, so nothing in the key UI or its backup text links the key to a Nostr identity.
- Tapping the SSH public-key line, the SSH fingerprint, or their copy icons places only that displayed public identifier on the system clipboard; no private-key material is copied.
- Key details expose the copyable SSH public-key line (without a comment), the copyable SSH public-key fingerprint, and the encrypted container's non-secret bcrypt KDF round count for verification. Key details also offer voluntary **Export Key to Notes** and **Export Key to Clipboard** actions that release the same passphrase-encrypted private key used during creation: the notes export sends the full self-describing text (PEM block plus key metadata) through the in-app target picker, and the clipboard export copies that same text. **Show Key as QR Code** uses the same passphrase gate and shows that same text as a QR code in a dialog, without copying it. The mandatory encrypted private-key export still happens during key creation and additionally requires the user to paste the saved key back.
- The key list refreshes when the app returns to the foreground, including after recovery work. Lists and details render from local storage only, so key names do not depend on relay or Brave Sync availability.
- The mandatory local-backup flow is split into **Export Key** and **Confirm Backup**. Back navigation is blocked on **Export Key**; Back from **Confirm Backup** returns to **Export Key** so the key can be sent again. The flow completes only after the export target accepted the text and the user pasted the saved key back and it matched the stored key. The paste check proves only that the user retained a readable copy: Android cannot confirm that the receiving app kept the text or that it remains available.
- The associated-key export contains the passphrase-encrypted OpenSSH private key and public key metadata in this exact line order: PEM begin marker, one-line Base64 key, PEM end marker, `unixTimestamp:` followed by the raw creation ID, `label:` followed by the key name (empty when unnamed), and `createdAt:` followed by the key-detail-style full date and time. It deliberately omits the key `npub`, and the Vault Key export omits its `npub` too. It remains sensitive: share recipients or anyone who learns the passphrase may be able to use the key.

## Current limitations

- Associated keys cannot be renamed, rotated, deleted, or manually restored one at a time.
- The app has no vault-reset action.
- The creation screen offers a Back link before creation starts; it does not remove an already-created key.
- The app persists a pending key ID before entering the backup sequence, then resumes the required export step after an app restart. Resuming always restarts at the export/choose-app phase; the paste-back confirmation must be completed again after a restart. It records only key IDs and cannot verify the durability, privacy, or future availability of a shared copy.
