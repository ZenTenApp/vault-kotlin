# ZenTen Vault — Product Brief

## 1. Purpose

ZenTen Vault is a personal key-vault product for people who use SSH credentials and want device-independent recovery without relying on a single vendor-controlled backup. A user begins with an existing encrypted Ed25519 OpenSSH private key. That key and its passphrase establish a deterministic master recovery identity. The vault then creates and manages additional SSH key pairs (sub-accounts) and backs all key material to two independent destinations:

1. encrypted, signed records on configured Nostr relays; and
2. Brave Sync password records, accessed through a sync code deterministically derived from the master identity.

The intended recovery promise is: **a user who retains the original master SSH private key and its passphrase can reconstruct the same vault identity and discover recoverable sub-accounts on a new device.**

## 2. Users and jobs to be done

### Primary user

A technically capable individual who already has an Ed25519 OpenSSH private key and wants to create, retain, inspect, export, and recover additional SSH keys with resilient remote backup.

### Core jobs

- Bring an existing SSH key into the vault without the vault generating a replacement master key.
- Confirm the SSH key's existing passphrase privately.
- Create a new SSH key pair quickly when a separate credential is needed.
- Copy or export the private/public material only through an explicit sensitive-data action.
- See whether a created account has reached each backup destination.
- Restore accounts discovered on remote backups after moving to or resetting a device.
- Reset a device-local vault without claiming that remote copies were deleted.

## 3. Product boundaries

### In scope

- First-run onboarding using a supplied Ed25519 OpenSSH-v1 private key.
- Paste, file import, and QR-based key acquisition where the platform supports each safely.
- Passphrase validation, deterministic master recovery identity creation, and setup rollback.
- Generation and local management of Ed25519 SSH sub-accounts.
- Nostr relay backup, discovery, repair, and restoration.
- Brave Sync backup and restoration.
- Backup-health visibility, retry behavior, locked-account handling, network/offline and device-time messaging.
- Pre-setup configuration of backup destinations, followed by configuration locking.

### Not product goals

- Becoming a general SSH-agent, terminal, server-login, Git, or certificate-management client.
- Editing, renaming, or rotating generated sub-account identities. Their labels intentionally remain canonical creation IDs.
- Creating a Nostr identity for every sub-account.
- Promising remote deletion when an account is deleted locally.
- Recovering the master SSH private key from derived words, a Nostr key, or a Brave Sync code. Derivation is one-way.
- Treating a device PIN, biometric prompt, or operating-system unlock as a replacement for the master SSH key passphrase.

## 4. Vocabulary

| Term | Meaning |
| --- | --- |
| **Master account / master identity** | The hidden root identity created from the user-supplied SSH key and passphrase. It signs and encrypts Nostr backups. It is not an item in the normal account list. |
| **Sub-account** | A new Ed25519 SSH key pair generated by ZenTen Vault. It has no Nostr key pair and no passphrase. |
| **Account ID / `createdAt`** | The canonical microsecond creation identifier of a sub-account. It is used as its label, local ID, key comment, route identifier, and remote backup identifier. |
| **Master SSH key** | The user-supplied OpenSSH-v1 Ed25519 private key that anchors the vault. |
| **Mnemonic** | A 24-word BIP39 phrase deterministically derived from the decrypted raw seed of the master SSH key. It is recovery material internal to the product, not a new user-entered secret. |
| **Master Nostr identity** | The secp256k1 key pair deterministically derived from the mnemonic. It signs and self-encrypts relay backup events. |
| **Brave Sync code** | A deterministic 25-word code derived from the mnemonic and used to access the Brave Sync chain. |
| **Pending restore** | A remotely discovered sub-account that is not yet local and awaits user confirmation to restore. |
| **Locked account** | A locally represented account that could not be made fully usable and must be re-fetched from backup. This is an exception state, not a normal account type. |
| **Remote backup** | A copy of an SSH private key stored as either an encrypted Nostr event or a Brave Sync password record. |

## 5. Product principles

1. **User-held root of trust.** The user brings the master key; the product does not manufacture the root identity.
2. **Deterministic recovery over account registration.** Recovery is based on held cryptographic material, not a ZenTen username, email, or cloud login.
3. **Redundancy without plaintext exposure.** Remote destinations receive protected backup material, never an intentionally plaintext key payload.
4. **Safe failure semantics.** A vault is not considered initialized until the mandatory master relay backup succeeds.
5. **Explicit disclosure.** Private keys are hidden by default and shown, copied, or exported only after an intentional confirmation.
6. **Stable interoperability.** Remote identifiers, record fields, and encryption behavior are product contracts, not implementation choices.
7. **Honest status.** Backup health reflects what was last confirmed, and unknown is different from missing.

## 6. Lifecycle at a glance

```text
New installation
  → import master SSH key
  → validate passphrase and derive recovery identity
  → publish mandatory encrypted master relay backup
  → initialize and attempt Brave Sync backup
  → lock destinations and discover existing sub-accounts
  → use vault
      → create sub-account
      → save locally immediately
      → back up asynchronously to both sources
      → monitor, retry, repair, or restore as needed
  → optional local reset / new-device recovery
```

## 7. Success measures

A release is product-ready only when a user can reliably:

- complete onboarding with a supported master key and correct passphrase;
- create a sub-account and immediately find it locally;
- observe each backup source's eventual result;
- recover remote sub-accounts after local vault data is erased;
- distinguish local deletion from remote backup retention; and
- complete the key flows using assistive technologies and without exposing secrets in ordinary UI, logs, or notifications.
