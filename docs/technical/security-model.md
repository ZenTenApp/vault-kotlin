# Security model

> This document records current security intent and review scope. It is not a security audit or a claim that the app is safe for production credentials before the [release gates](../stakeholder/scope-and-roadmap.md#release-gates-before-production-use) are met.

## Protected assets

- User-provided Vault Key private key and its passphrase.
- Derived recovery material and the vault-key Nostr identity; both are recomputed from the encrypted key on demand and never stored.
- Generated associated-account SSH private keys, encrypted in their OpenSSH containers with the Vault Key passphrase.
- Brave Sync recovery/access material.
- Remote backup payloads and local backup-status metadata.

## Trust boundaries

| Boundary | Expected protection | Review focus |
| --- | --- | --- |
| User input and UI | Private material is not revealed by default. | Screenshots, accessibility, clipboard, backgrounding, error text. |
| Device storage | Secrets are stored through Android Keystore-backed AES-GCM storage. | Keystore behavior, backup policy, migration, corruption, device compromise. |
| Crypto/derivation | Deterministic behavior must remain compatible. | Input normalization, library versions, vectors, zeroization limits. |
| Network and relays | Payloads are protected before transmission. | Authentication/signatures, encryption, relay trust, replay/malformed records. |
| Backup record metadata | Deliberately readable data is limited to the account label and creation ID on that account's backup records. | Accepted lack of in-flow disclosure, replication/deletion limits, relay and Brave Sync server trust. |
| Brave Sync integration | Records and transport protect remote data. | Protocol compatibility, authentication, server trust, retry/error behavior. |
| Logs and operations | Secrets must not leave through diagnostics. | Crash reporting, analytics, build logs, support workflows. |
| KeyHive provider | Trusted sibling apps may read associated SSH private keys and account labels. | Signature identity, field allowlist, plaintext Binder IPC, provider process. |

## Current safeguards visible in code

- The interactive UI requires Android system authentication with a strong biometric or device PIN, pattern, or password. On API 28–29, where Android cannot combine the two in one prompt, the prompt accepts a strong biometric only and falls back to the keyguard's credential prompt, so a Class 2 biometric is never accepted. It always locks on cold/process start, and returning to the foreground after more than 30 seconds in the background requires authentication again and drops the foreground passphrase session. The boundary is checked on foreground return, not by a timer, and a continuously foregrounded app is not locked for inactivity. Devices without an accepted secure lock are blocked until one is configured. Unlock state and monotonic grace timing are memory-only, and a configuration change (rotation, theme or dark-mode switch, locale or font-size change) recreates the Activity without dropping that session, so it does not re-prompt; process death still relocks. Prompt errors that mean the device cannot satisfy the policy route to mandatory enrollment; cancellation and retryable errors stay locked.
- When a VaultKey is stored, device authentication is followed by a VaultKey passphrase gate. The passphrase is **never persisted**: `VaultKeySession` holds it in memory for the session, verifies it by decrypting the stored VaultKey (not by comparing against a stored copy), and zeroes the foreground copy when the session relocks or the process dies. Work that started while the session was unlocked holds an independent copy, may finish after the foreground session locks, and zeroes that copy in a `finally` block; work that has not started when the session locks fails closed and stays pending for the next unlock. A fresh install skips the gate and collects the passphrase during onboarding.
- `MainActivity` applies `FLAG_SECURE` for its full lifetime, protecting screenshots, screen recording, and Recents previews where Android supports it. Sensitive screens no longer clear the flag on exit.
- The device-authentication gate is an interactive UI control only. The Keystore-backed AES-GCM store (`KeystoreCryptoService` behind `SecureStorageService`) keeps one self-describing encrypted record per account and no separate account index, so each save or removal is a single atomic preference edit and concurrent writers cannot orphan each other's records. It is deliberately not bound to user authentication because signature-authorized KeyHive provider access is an approved requirement. Background consolidation no longer runs unattended: it takes the passphrase from the in-memory session and fails closed when no session is unlocked. Root, forensic, compromised-process, and trusted-sibling-app access are outside this gate.
- Backup records are the only routine path that sends readable account data off the device. The account's kind `37802` relay event carries the user's account name in a plain `label` tag, and its Brave Sync record carries a `label:<name>` note; both are readable by anyone who can list that account's records, without the Vault Key passphrase. The encrypted key payload does not contain the name. There is no kind `0` profile or kind `10050` DM relay list publication. Per decision D4 the **Create New Account** screen deliberately carries no disclosure, to keep the creation UI minimal; the readable fields are documented here and in the feature and stakeholder docs instead. Relays and Brave Sync servers can re-publish or mirror those records, so the app cannot promise deletion.
- Private-key/passphrase setup screen sets Android's secure-window flag.
- Account-detail private-key export requires re-entering the account passphrase and emits only the passphrase-encrypted OpenSSH key, never plaintext; the screens are screenshot-protected.
- Local private-key export keeps the secure-window flag, prioritizes installed supported note apps without excluding other compatible Sharesheet targets, and sends a self-describing text export. The voluntary account-detail exports — **Export Account to Notes**, which opens the target picker, and **Export Account to Clipboard**, which places the encrypted key as an OpenSSH PEM block on the clipboard without the metadata the notes export appends — and the voluntary **Export VaultKey to Notes** action on the Vault Key screen require the user to re-enter the passphrase protecting that account or Vault Key before the export runs; the entered value is verified by decrypting the record and never retained. The mandatory creation-time exports do not re-ask, because the passphrase was just entered to create the record; they instead require the user to paste the saved key back, and that confirmation is an attestation, not verification that the receiving app retained the key.
- OpenSSH parsing, Nostr derivation/encryption, and remote record codecs have automated tests; crypto test vectors are in `app/src/test/resources/golden/`.
- Generated associated-account OpenSSH keys use `aes256-ctr` with `bcrypt_pbkdf` and the retained vault-key passphrase; Nostr backups add NIP-44 encryption around that encrypted key payload.
- A generated VaultKey's passphrase must clear a length floor and a zxcvbn guessability floor before any key is created (`VaultKeyPassphrasePolicy`, `PassphraseStrengthChecker`). **Paste VaultKey** and **Recover VaultKey** enforce the same two floors before importing or querying any remote copy (D9). The estimate is computed on-device with no network call and no breach-list lookup, using a wipeable buffer cleared after matching. The `PassphraseStrength` projection reaches the UI through the graph-scoped ViewModel's state and carries, per match, the matched text along with the kind, span, cost, and per-pattern attributes (dictionary and rank, keyboard and turns, repeat count, run direction). It deliberately carries passphrase fragments: the **Passphrase strength** sheet names the sequence that matched, because a pattern and a span alone cannot tell `alice@` from any other six-character run. The consequence is that this state holds passphrase content while the step is on screen, which the rest of the wizard's state deliberately avoids; it is never persisted or logged, and it is dropped when the step is left. `Strength.password` and the de-obfuscated `Match.matchedWord` are still not carried. Dictionary name plus rank is kept as the key diagnostic for a dictionary hit, which is only a lookup away from the matched word with the dictionary file in hand. Passphrases longer than 256 characters are refused rather than measured so the pattern search cannot be driven to unbounded work. The onboarding steps' feedback state carries only this projection and no copy of the typed text; the submit path re-measures the passphrase it was given instead of trusting the preview.
- Sensitive records are encrypted with AES-256-GCM using a non-exportable Android Keystore key. Each write uses a fresh Keystore-generated IV, and a version byte allows the payload format to evolve without misreading older data.
- Local secure storage, source adapters, consolidation, and background scheduling have distinct implementation areas.
- NIP-42 relay challenges are signed transiently with the operation's Nostr identity and are not persisted. Every Vault Key record operation (`kind` 37801) — the initial create-flow backup, imported-key setup, retries, and later consolidation — uses the identity derived from the recoverable 24-word `vkbckp` (Vault Key BacKup) associated-account mnemonic, so every run addresses the same recoverable relay record; associated-account records (`kind` 37802) use the Vault Key's original-seed identity. Neither identity is stored on an `Account`: `DefaultBackupSourceFactory` derives both from the decrypted seed once per engine run, and exports derive the Vault Key `npub` on demand from the passphrase the user re-enters.
- `RemoteOperationPrecondition` gates activity navigation, WorkManager consolidation, and the in-process `SetupService` (setup, retry, and create-flow backup) paths before timestamped remote authentication unless Android reports a system-validated internet connection and the clock is within two minutes of a HTTPS response's server time. It uses the first HTTP `Date` header returned by Google or Cloudflare and compensates for half the observed request round-trip time. The foreground gate re-checks on creation, resume, network changes, and system clock/timezone changes, so a mid-session manual clock change cannot leave a stale "correct time" assurance visible. Gated paths skip or fail without producing Nostr or Brave timestamped authentication when connectivity is not validated or skew is known bad; setup retains the locally committed Vault Key so the user can retry. If neither source responds, the app allows access/work because it cannot establish that the device clock is wrong. The block screen identifies each proven unmet prerequisite without exposing vault data. TLS protects the response in transit, but this is not independent proof that either endpoint's clock or the network is trustworthy.
- Backup status, pending writes, and checkpoints persist only canonical account/source IDs, coarse state/error categories, counters, and timestamps—not keys, passphrases, payloads, sync codes, auth tokens, or challenges.
- Presence comparisons are identifier-only. A remote private-key payload is decrypted only when its associated account is absent locally and restoration is required.
- The KeyHive provider exposes only associated-account `createdAt`, `zentenKey`, and `accountName` fields as `json_v1` through a signature-protected ContentProvider. The signature permission is the IPC confidentiality boundary; certificate-derived application encryption is not used because the certificate is public. Vault Key material, passphrases, mnemonics, and SSH public keys are not exposed, and neither is the account's Nostr identity: it is derived on demand from the decrypted seed rather than stored, so no identity field exists for the provider to serve. The account label is shared so sibling apps can display the account, and it is no more readable there than on the account's own backup records.
- Dependency and source scanning is free-tier: Dependabot alerts and security updates are enabled, and CI runs Gitleaks (full git history) and Semgrep (Kotlin/Android, ERROR-severity gate). GitHub's paid code and secret scanning are unavailable on the Free private-repo plan. Configuration and limits are documented in [Build and test](build-and-test.md#dependency-and-security-scanning).

## Required production review topics

1. Threat model for a stolen, unlocked, rooted, or malware-infected device.
2. Secure-storage and Android backup configuration on all supported OS versions.
3. Clipboard retention, screenshot/task-switcher behavior, accessibility exposure, and automatic hiding of sensitive content.
4. Remote-data validation, signature checks, encryption compatibility, downgrade/replay behavior, and denial-of-service limits.
5. Network timeouts, retries, offline state, remote-service compromise/outage, and status accuracy.
6. Secret handling in logs, telemetry, analytics, crash reporting, CI, support, and release builds, including coverage gaps left by the free-tier scanners (no push protection, no Security-tab dashboard, runtime-fetched Semgrep rules).
7. Independent cryptography and protocol review before production use.
8. ~~Whether interactive private-key disclosure should use a separate authentication-bound encryption domain, given that KeyHive provider access must remain unattended.~~ **Closed as not planned (D5).** Same-signature unattended access is an accepted requirement; see [KeyHive provider](key-hive-provider.md#accepted-decision-d5). Signing-key custody and sibling-app review are the controls for that boundary.
9. ~~Whether **Paste VaultKey** and **Recover VaultKey** should enforce the creation passphrase policy, warn, or prompt for acknowledgement when the supplied passphrase is weak.~~ **Closed as enforced (D9, reversed 2026-11-09).** Both paths now apply the same length and zxcvbn floors as creation, and a passphrase below either floor is refused: no key is stored, and no relay or Brave Sync source is queried. The original carve-out accepted a weak passphrase because the artifact belongs to the user, the app offers no in-app re-encryption, and gating could strand someone holding a valid key. That reasoning predates any installation: Vault is still pre-release with no users, so nothing in the field can be refused, while the cost of the carve-out is a backup that leaves the device protected only by a guessable string. Import re-measures at submit rather than trusting the debounced preview, so acceptance never depends on UI timing. Both steps show the same meter and details sheet as creation, and the refusal names the rule that failed. See [Vault Key setup](../features/vault-key-setup.md#failure-and-security-expectations).
10. ~~What floor the `bcrypt_pbkdf` work factor should have, given the Settings menu offered every power of two from 1 to 8192.~~ **Closed as decided (D12, recorded 2026-11-04; revised 2026-11-09).** The work factor is bounded to `128`–`8192` for generation, selection, **and parsing**. Generation and the Settings menu offer only the powers of two in that band, defaulting to 128; the metadata reader accepts any declared count in the band (a range check, not a menu lookup) and rejects anything outside it before `bcrypt_pbkdf` runs. The floor is 128 because 128 is the default and keeps a container at roughly a second of deliberate work, while a weaker declared factor would be cheap to attack offline once a key is exported to Notes, the clipboard, or a sibling app. The ceiling is both a policy limit and a denial-of-service control: the work factor is attacker-controlled metadata trusted before any password is checked, so a container declaring `2,147,483,647` rounds would otherwise block every unlock and recovery attempt. The original carve-out letting parsing accept weaker foreign keys (down to 1) because `ssh-keygen` defaults to 16 rounds was removed in the 2026-11-09 revision: Vault is still pre-release and holds no older keys, so every container it can encounter was either generated inside the band or is rejected at intake — **Paste VaultKey**, **Recover VaultKey**, and associated-account restore alike. See [SSH key seed derivation](ssh-key-seed-derivation.md#associated-account-generating-a-new-ssh-key).

## Non-promises

- Device authentication is currently an interactive UI gate, not an authentication-required Keystore wrapper around stored vault data. It does not replace the Vault Key private key and passphrase for recovery, or change signature-authorized KeyHive provider access. Background consolidation is restricted indirectly: it requires an unlocked in-memory passphrase session and fails closed otherwise. A job that started while unlocked receives an independent passphrase copy, continues to completion after the foreground session locks, and zeroes the copy when it finishes; a queued job that has not started when the session locks fails closed and remains pending for the next unlock. The 30-second boundary is evaluated on the next foreground return rather than by a timer, and a continuously foregrounded app is not locked for inactivity. The interactive lock does not gate KeyHive provider access.
- Remote backup does not guarantee availability. Vault Key setup requires one eligible Nostr and one eligible Brave source, not successful writes to every source. The current app has no account-deletion or vault-reset action.
- The account label is not private. The account name and creation ID are readable in plaintext on that account's relay backup event (`label` and `d` tags respectively) and on Brave Sync servers (URL, username, and `label:<name>` note), so they are visible to anyone who queries or holds those records; the creation screen deliberately does not disclose it (D4), and deletion cannot be guaranteed.
- The application cannot recover Vault Key material the user has lost **outright**. A forgotten passphrase has no reset path, and a key held by neither the private key nor the 24 Secret Combinations cannot be recreated. It *can* restore a lost private key when the Secret Combinations and passphrase are still available; the remote copy is decrypted with that passphrase and is unreadable without it.
- Every application signed with Vault's trusted release certificate can read each shared associated SSH private key. A compromised trusted sibling app or device is outside this protection boundary. This is an accepted product requirement (D5), not a gap: the provider shares only the passphrase-encrypted OpenSSH container and the account label, never the passphrase or the account's Nostr identity, and it serves reads without device authentication or an unlocked session. A separate authentication-bound encryption domain is not planned.

## Change control

Changes to derivation, remote record formats, secure storage, or sensitive UI behavior require security review, compatibility tests, and updates to the relevant feature and stakeholder documentation.
