# Implementation status

This is a repository-oriented status view for a pre-release production build. It is not a production-readiness certification, and **present in code** does not imply completed security, interoperability, UX, or operational validation.

| Area | Status | Repository evidence | Notes |
| --- | --- | --- | --- |
| Device authentication and foreground lock | Present in code | `ui/auth/`, `MainActivity.kt` | Strong biometric or device credential is mandatory; returning to the foreground after more than 30 seconds in the background requires authentication again and drops the foreground passphrase session (evaluated on return, not by a timer), prompt errors are classified, pre-API-30 capability is handled via the keyguard, the entire activity is screenshot protected, and an Activity recreation from a configuration change retains the in-memory unlock session instead of re-prompting (process death still relocks). This is an interactive UI gate rather than authentication-bound storage. Consolidation workers require the in-memory passphrase session and fail closed when it is locked; KeyHive provider access remains unattended. |
| Compose navigation and main screens | Present in code | `ui/`, `VaultNavGraph.kt` | Onboarding (including the in-app Create VaultKey wizard and **Recover VaultKey**), key list/create/detail, Settings (including the Secret Combinations review), and dedicated Vault Key details are implemented. |
| Vault Key intake | Present in code | `ui/onboarding/`, `domain/SetupService.kt`, `ui/root/RootScreen.kt` | Paste-oriented; retains validated Vault Key and supports retry when source quorum fails. `AppStorageService.importedVaultKeySetupPending` makes a committed-but-unbacked import durable, so the retry action is offered on failure and the launch router resumes the retry state after process death instead of returning to Get started; parse/derivation failures persist nothing and offer no stored-key retry. |
| In-app VaultKey generation wizard | Implemented | `ui/onboarding/createvaultkey/` | Consent, a length-and-guessability passphrase policy (`VaultKeyPassphrasePolicy`, zxcvbn-backed `PassphraseStrengthChecker`), passphrase creation and verification, a non-dismissible creation screen with stage and per-source sync progress, generated-key persistence and remote backup attempts, local **Create Backup** export, pasted-key **Confirm Backup** verification with an escalating wrong-paste lockout (1/2/3 minutes, then back to export), grouped BIP-39-index transcription, sequential re-entry verification, and setup completion are implemented. Completion is gated on the relay-plus-Brave backup quorum: `SetupService.completeGeneratedVaultKeySetup` refuses it until `AppStorageService.vaultKeyQuorumReached` is true, and the final screen offers **Retry VaultKey backup** instead of advancing when the create-flow backup never landed. |
| Secret Combinations review | Implemented | `ui/secretcombinations/`, `ui/settings/SettingsScreen.kt` | A **Secret Combinations** item in Settings starts a passphrase-gated flow that re-displays the 24 BIP-39 positions and requires the user to re-enter them. Once the passphrase gate passes, the flow blocks Back and persists its step so a restart resumes it; the marker clears on successful verification. |
| OpenSSH Ed25519 parsing/passphrase validation | Present in code | `crypto/SshKeyCodec.kt`, tests | Requires production crypto/dependency review. Parsing and every key-intake path accept only containers whose declared `bcrypt_pbkdf` work factor is 128–8192 rounds. |
| Deterministic recovery identity | Present in code | `crypto/Seedify.kt`, `NostrKeyDerivation.kt` | Golden/parity tests exist. |
| Secure local storage | Present in code | `data/secure/`, `data/kv/` | Device and backup-policy review remains required for the interactive gate, but migration policy is now declared: `dataExtractionRules` excludes every domain from cloud backup and D2D transfer, and an unreadable-vault state routes to `StrandedVaultScreen` rather than onboarding. See [Device migration and backup](../features/device-migration-and-backup.md). |
| Associated-key generation/listing | Present in code | `domain/KeyService.kt`, `ui/keys/`, `domain/BackupService.kt` | Local-first persistence; cards show the stored key name, and a restored record without a label shows neither the avatar nor a name rather than the shortened npub. The associated key's npub is not displayed, copied, or exported, and its SSH public-key line has no comment. The name is stored on the key's backup record — a plain `label` tag on its kind 37802 relay event and a `label:<name>` note on Brave Sync — so restoration keeps it; there is no kind 0 profile or kind 10050 DM relay list publication, and no relay profile reads. The creation screen deliberately does not disclose the readable label (D4). |
| Encrypted private-key export and local backup | Partial | `ui/keys/KeyDetailScreen.kt`, `ui/keys/LocalKeyBackupScreen.kt` | Confirmation and screenshot protection exist, and the app never reveals or copies a plaintext private key. The voluntary key-detail exports require the user to re-enter the passphrase that protects the key before either runs: **Export Key to Notes** opens the target picker, and **Export Key to Clipboard** copies the same self-describing encrypted-key text the notes export sends to the clipboard on explicit request, flags the clip as sensitive, and clears it again after 60 seconds. **Show Key as QR Code** and **Show VaultKey as QR Code** display that text as a QR code in a dialog. The mandatory creation-time local backup exports the encrypted OpenSSH private key and then requires the user to paste it back before the key can be used. The in-app target picker prefers installed supported note apps and bypasses the Android Sharesheet; independent verification of delivery remains unavailable. Passphrase verification and Vault Key export run off the main thread, and the confirmation dialog shows a busy, non-interactive Confirm state while the bcrypt derivation is in flight. |
| Independent Nostr source adapter | Present in code | `domain/BackupSourceAdapters.kt`, `network/nostr/` | Includes transient NIP-42 handling; both default relays still require opt-in operational interoperability validation. |
| Independent Brave-compatible source adapter | Present in code | `domain/BackupSourceAdapters.kt`, `domain/BraveSyncBackupService.kt` | Both default litesync endpoints require end-to-end infrastructure validation. |
| Source repository/default policy | Present in code | `domain/BackupSources.kt`, `domain/BackupSourceRepository.kt` | Four immutable defaults (two Nostr relays and two litesync Brave Sync endpoints) are enabled, trusted for restore, and count toward the Vault Key quorum. Custom-source persistence exists in the domain layer, but no custom-source management UI is exposed; see [backup source management](../features/backup-source-management.md). |
| Two-phase consolidation and retry | Present in code | `domain/KeyConsolidationEngine.kt`, `background/BackupWorkers.kt` | Sequential restore-before-backup, triggered after each unlocked launch; lifecycle/failure validation should continue. |
| Separate Vault Key consolidation | Present in code | `domain/KeyConsolidationEngine.kt`, `background/BackupWorkers.kt` | Vault Key records use the `vkbckp` Vault Key backup relay identity and have their own post-unlock worker, freshness window, and manual action, independent of key consolidation. |
| In-memory passphrase session | Present in code | `domain/VaultKeySession.kt`, `ui/auth/VaultUnlockGateViewModel.kt` | The VaultKey passphrase is never persisted; it is verified by decrypting the stored key, held in memory for the session, and re-entered after relock or process death. |
| Per-source status UI | Partial | `ui/keys/KeyDetailScreen.kt`, `ui/vaultkey/VaultKeyDetailScreen.kt` | Live rows exist; final accessible copy, timestamps, and remediation need product validation. |
| Automatic associated-key recovery | Present in code | `domain/KeyConsolidationEngine.kt`, source adapters | Trusted-source candidates restore automatically; real-service end-to-end validation remains. A record whose key falls outside the accepted 128–8192 bcrypt work-factor band is skipped at intake like any other invalid record. |
| Key deletion and vault reset | Not available | — | Neither action is currently provided. The stranded-vault action is not a reset: it retains unreadable ciphertext under a single quarantine generation and only clears launch-routing flags. When the cause is an unreadable Keystore it offers a re-check instead and sets nothing aside. |
| Export/share workflow | Partial | `ui/keys/LocalKeyBackupScreen.kt`, `ui/vaultkey/VaultKeyDetailScreen.kt` | The voluntary **Export VaultKey to Notes** action first requires the VaultKey passphrase. An in-app picker then lists compatible text targets, prefers installed supported note apps, and launches the selected activity explicitly. This preserves the encrypted OpenSSH private key as text without showing the Android Sharesheet's Copy action. The key-detail **Export Key to Notes** action follows the same pattern after re-entering the key passphrase, and **Export Key to Clipboard** places the encrypted key as an OpenSSH PEM block, without the metadata, on the clipboard instead. User confirmation is required after export, but cannot prove that a target saved the key. |

See the [stakeholder scope and roadmap](../stakeholder/scope-and-roadmap.md) for client-review context.
