# Implementation status

This is a repository-oriented status view for a pre-release production build. It is not a production-readiness certification, and **present in code** does not imply completed security, interoperability, UX, or operational validation.

| Area | Status | Repository evidence | Notes |
| --- | --- | --- | --- |
| Device authentication and foreground lock | Present in code | `ui/auth/`, `MainActivity.kt` | Strong biometric or device credential is mandatory; returning to the foreground after more than 30 seconds in the background requires authentication again and drops the foreground passphrase session (evaluated on return, not by a timer), prompt errors are classified, pre-API-30 capability is handled via the keyguard, and the entire activity is screenshot protected. This is an interactive UI gate rather than authentication-bound storage. Consolidation workers require the in-memory passphrase session and fail closed when it is locked; KeyHive provider access and automatic profile publication remain unattended. |
| Compose navigation and main screens | Present in code | `ui/`, `VaultNavGraph.kt` | Onboarding, pre-setup source list/add, account list/create/detail, and dedicated Vault Key details are implemented. |
| Vault Key-account key intake | Present in code | `ui/onboarding/`, `domain/SetupService.kt` | Paste-oriented; retains validated Vault Key and supports retry when source quorum fails. |
| In-app VaultKey generation wizard | Implemented | `ui/onboarding/createvaultkey/` | Consent, a length-and-guessability passphrase policy (`VaultKeyPassphrasePolicy`, zxcvbn-backed `PassphraseStrengthChecker`), passphrase creation and verification, a non-dismissible creation screen with stage and per-source sync progress, generated-key persistence and remote backup attempts, local **Create Backup** export, pasted-key **Confirm Backup** verification with an escalating wrong-paste lockout (1/2/3 minutes, then back to export), grouped BIP-39-index transcription, sequential re-entry verification, and setup completion are implemented. |
| Secret Combinations review | Implemented | `ui/secretcombinations/`, `ui/settings/SettingsScreen.kt` | A **Secret Combinations** item in Settings starts a passphrase-gated flow that re-displays the 24 BIP-39 positions and requires the user to re-enter them. Once the passphrase gate passes, the flow blocks Back and persists its step so a restart resumes it; the marker clears on successful verification. |
| OpenSSH Ed25519 parsing/passphrase validation | Present in code | `crypto/SshKeyCodec.kt`, tests | Requires production crypto/dependency review. |
| Deterministic recovery identity | Present in code | `crypto/Seedify.kt`, `NostrKeyDerivation.kt` | Golden/parity tests exist. |
| Secure local storage | Present in code | `data/secure/`, `data/kv/` | Device, migration, and backup-policy review remains required. |
| Associated-account generation/listing | Present in code | `domain/AccountService.kt`, `ui/accounts/` | Local-first persistence; labels currently use creation IDs. |
| Private-key reveal/copy/local backup | Partial | `ui/accounts/AccountDetailScreen.kt`, `ui/accounts/LocalAccountBackupScreen.kt` | Confirmation and screenshot protection exist. The voluntary account-detail exports require the user to re-enter the passphrase that protects the account before either runs: **Export Account to Notes** opens the target picker, and **Export Account to Clipboard** copies the encrypted key as an OpenSSH PEM block (markers around the single-line Base64 body, without the account metadata) to the clipboard on explicit request. The mandatory local backup requires a text export of the encrypted OpenSSH private key followed by user confirmation that it was saved. The in-app target picker prefers installed supported note apps and bypasses the Android Sharesheet; independent verification of delivery remains unavailable. |
| Independent Nostr source adapter | Present in code | `domain/BackupSourceAdapters.kt`, `network/nostr/` | Includes transient NIP-42 handling; both default relays still require opt-in operational interoperability validation. |
| Independent Brave-compatible source adapter | Present in code | `domain/BackupSourceAdapters.kt`, `domain/BraveSyncBackupService.kt` | All three endpoints require end-to-end infrastructure validation. |
| Source repository/default policy | Present in code | `domain/BackupSources.kt`, `BackupSourceRepository.kt`, `ui/sources/` | Five immutable defaults and custom-source persistence. The UI currently adds at most three pre-setup Nostr relays; broader repository operations and custom Brave support are not exposed. |
| Two-phase consolidation and retry | Present in code | `domain/AccountConsolidationEngine.kt`, `background/BackupWorkers.kt` | Sequential restore-before-backup, triggered after each unlocked launch; lifecycle/failure validation should continue. |
| Separate Vault Key consolidation | Present in code | `domain/AccountConsolidationEngine.kt`, `background/BackupWorkers.kt` | Vault Key records use the `vkbckp` Vault Key backup relay identity and have their own post-unlock worker, freshness window, and manual action, independent of account consolidation. |
| In-memory passphrase session | Present in code | `domain/VaultKeySession.kt`, `ui/auth/VaultUnlockGateViewModel.kt` | The VaultKey passphrase is never persisted; it is verified by decrypting the stored key, held in memory for the session, and re-entered after relock or process death. |
| Per-source status UI | Partial | `ui/accounts/AccountDetailScreen.kt`, `ui/Vault Key/` | Live rows exist; final accessible copy, timestamps, and remediation need product validation. |
| Automatic associated-account recovery | Present in code | `domain/AccountConsolidationEngine.kt`, source adapters | Trusted-source candidates restore automatically; real-service end-to-end validation remains. |
| Account deletion and vault reset | Not available | — | Neither action is currently provided. |
| Export/share workflow | Partial | `ui/accounts/LocalAccountBackupScreen.kt`, `ui/vaultkey/VaultKeyDetailScreen.kt` | The voluntary **Export VaultKey to Notes** action first requires the VaultKey passphrase. An in-app picker then lists compatible text targets, prefers installed supported note apps, and launches the selected activity explicitly. This preserves the encrypted OpenSSH private key as text without showing the Android Sharesheet's Copy action. The account-detail **Export Account to Notes** action follows the same pattern after re-entering the account passphrase, and **Export Account to Clipboard** places the encrypted key as an OpenSSH PEM block, without the metadata, on the clipboard instead. User confirmation is required after export, but cannot prove that a target saved the key. |

See the [stakeholder scope and roadmap](../stakeholder/scope-and-roadmap.md) for client-review context.
